# BooksTrack iOS - Planning Files Directory

**Purpose:** Centralized location for all planning documents (task plans, findings, progress tracking)

**Tech Stack:** SwiftUI, Core Data, CloudKit, Swift Concurrency (@Observable, async/await, actors)

**Project Type:** iOS app for personal book tracking (solo-dev, family app)

---

## Overview

This directory stores planning artifacts generated by:

1. **Native Claude Code Plans** - Built-in planning mode (simple tasks)
2. **planning-with-files Plugin** - Manus-style planning for complex tasks (task_plan.md, findings.md, progress.md)

Both systems write to `.claude/plans/` to avoid root directory clutter.

---

## When to Use Each System

### Native Plans (Simple Tasks)
Use for straightforward, single-file changes:
- Bug fixes in isolated views
- Simple UI tweaks (colors, spacing)
- Adding a single computed property
- Minor refactoring within one file

**Example:**
```
"Fix the book cover aspect ratio in BookDetailView"
→ Creates .claude/plans/fix-cover-aspect-ratio.md
```

### planning-with-files Plugin (Complex Tasks)
Use for multi-phase work requiring research and coordination:
- Feature implementations across multiple files (e.g., adding CloudKit sync)
- Architecture changes (migrating from Core Data to SwiftData)
- Migration projects (iOS 17 → iOS 18 API updates)
- Performance optimization requiring analysis

**Example:**
```
"Implement CloudKit sync for book collection"
→ Creates:
  - .claude/plans/cloudkit-sync/task_plan.md (phases, dependencies)
  - .claude/plans/cloudkit-sync/findings.md (research notes)
  - .claude/plans/cloudkit-sync/progress.md (completion tracking)
```

## iOS/Swift Planning Considerations

### Swift Concurrency
- **@Observable vs @StateObject**: Plan data flow patterns before implementation
- **@MainActor boundaries**: Identify where UI updates must be main-thread
- **Actor isolation**: Plan concurrent access to shared state
- **async/await chains**: Map async dependencies in task_plan.md

### Core Data / SwiftData
- **Schema migrations**: Always plan migration paths (lightweight vs heavyweight)
- **Background contexts**: Document which operations need background threads
- **Fetch request optimization**: Profile before optimizing (use findings.md for metrics)

### SwiftUI
- **View decomposition**: Plan component hierarchy before building
- **State management**: Document data flow (parent → child, environment objects)
- **Preview data**: Plan mock data structures for Canvas previews

### CloudKit
- **Schema design**: Plan record types and relationships upfront
- **Sync conflicts**: Document conflict resolution strategy
- **Privacy zones**: Plan data compartmentalization (private vs shared)

## File Naming Conventions

### Native Plans
```
.claude/plans/<task-slug>.md
```

Examples:
- `fix-navigation-bar-tint.md`
- `add-genre-filter.md`
- `update-swiftui-lifecycle.md`

### Plugin Plans (Manus-style)
```
.claude/plans/<project-slug>/
  ├── task_plan.md
  ├── findings.md
  └── progress.md
```

Examples:
- `cloudkit-sync/` - Multi-phase CloudKit integration
- `swiftdata-migration/` - Core Data → SwiftData migration
- `ios18-updates/` - Platform API updates

## Workflow Integration

### Session Start Hook
`.claude/hooks/session-start.sh` automatically checks for active plans:
- Lists incomplete native plans
- Shows in-progress plugin tasks (from progress.md)
- Surfaces blocked tasks requiring attention

### Safe Testing Policy
**CRITICAL:** Plans involving build/test steps MUST use safe commands:
- Use `/quick-validate` (not `/build`)
- Use `/sim-safe` (not `/sim`)
- Use `/device-deploy` for real device testing

Plans should document test strategy in task_plan.md Phase sections.

## Best Practices

### 1. Research Before Implementation
Use findings.md to document:
- Apple documentation references (WWDC videos, API docs)
- Stack Overflow solutions (capture URLs + code snippets)
- Existing codebase patterns (grep results, file locations)

### 2. Plan for Testability
In task_plan.md, include test phases:
- **Unit tests**: ViewModels, business logic (quick-validate)
- **UI tests**: SwiftUI view rendering (sim-safe)
- **Integration tests**: Core Data + CloudKit (device-deploy for real backend)

### 3. Document Decisions
Capture architectural decisions in findings.md:
- Why @Observable over ObservableObject
- Why Core Data instead of SwiftData (or vice versa)
- Why manual async/await instead of Combine

Future you (or future Claude) will thank you.

### 4. Track Dependencies
In task_plan.md, explicitly note:
- Third-party package versions (SPM dependencies)
- Minimum iOS deployment target
- Required Xcode version
- CloudKit schema version dependencies

## Example: Multi-Phase Planning

### Task: Implement Offline Reading Mode

**Step 1: Initialize Plugin Planning**
```
User: "Implement offline reading mode with local chapter caching"
Claude: [Uses planning-with-files plugin]
```

**Step 2: Research Phase (findings.md)**
```markdown
## Offline Caching Research

### URLCache API (Built-in)
- Pros: Zero dependencies, automatic HTTP cache
- Cons: No fine-grained control, cache eviction unpredictable
- Reference: https://developer.apple.com/documentation/foundation/urlcache

### NSPersistentContainer (Core Data)
- Pros: Already using for book metadata, transactional
- Cons: Not optimized for blob storage (chapters are text)
- Current schema: Book, Author, Genre entities

### FileManager (Direct file storage)
- Pros: Simple, efficient for text files
- Cons: Manual cleanup, no automatic sync
- Strategy: Store in Documents/OfflineChapters/{bookISBN}/{chapterNum}.txt

### Decision: FileManager with Core Data index
Store chapter text in files, track metadata in Core Data (download date, file path).
```

**Step 3: Task Plan (task_plan.md)**
```markdown
## Phase 1: Core Data Schema Migration
- [ ] Add `cachedChapters` relationship to Book entity
- [ ] Create `CachedChapter` entity (chapterNum, filePath, downloadDate)
- [ ] Generate migration mapping model
- [ ] Test lightweight migration with sample data

## Phase 2: File Storage Manager
- [ ] Create `OfflineChapterManager` actor
- [ ] Implement `saveChapter(_:for:bookISBN:)` async method
- [ ] Implement `loadChapter(num:bookISBN:)` async throws method
- [ ] Add storage quota management (max 500MB)

## Phase 3: UI Integration
- [ ] Add download button to ChapterListView
- [ ] Show download progress in ChapterRow
- [ ] Add offline indicator in BookDetailView
- [ ] Handle offline mode in ChapterReaderView

## Phase 4: Background Download
- [ ] Implement URLSession background configuration
- [ ] Add "Download All" option for books
- [ ] Handle app termination during download

## Testing Strategy
- Phase 1: Unit tests for migration (quick-validate)
- Phase 2: Actor isolation tests (quick-validate)
- Phase 3: SwiftUI preview tests (sim-safe)
- Phase 4: Background download test (device-deploy - need real app lifecycle)
```

**Step 4: Progress Tracking (progress.md)**
```markdown
## Completion: 2/4 phases (50%)

### ✅ Phase 1: Core Data Schema Migration
- Schema updated, lightweight migration works
- 15 unit tests passing

### ✅ Phase 2: File Storage Manager
- `OfflineChapterManager` actor implemented
- Storage quota manager operational
- 23 unit tests passing

### 🚧 Phase 3: UI Integration (In Progress)
- Download button added to ChapterListView
- BLOCKED: Need design review for progress indicator
  - Options: Circular progress vs linear bar
  - Recommendation: Linear bar (matches Apple Books)

### ⏸️ Phase 4: Background Download (Not Started)
- Waiting for Phase 3 completion
```

## Troubleshooting

### "Plans directory not found"
- Check `.claude/settings.json` has `"plansDirectory": ".claude/plans"`
- Verify directory exists: `ls -la /Users/juju/dev_repos/books-v3/.claude/plans`

### "Native plans creating files in root directory"
- Restart Claude Code session (settings.json changes require restart)
- Check no typos in settings.json (use `jq . .claude/settings.json` to validate)

### "Planning plugin not triggering"
- Use explicit trigger words: "implement feature", "multi-step", "phase"
- Check `.claude/rules/planning-automation.md` for trigger keywords
- Manually invoke: `/planning-with-files` slash command
